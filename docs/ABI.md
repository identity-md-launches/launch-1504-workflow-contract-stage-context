# ABI and frontend integration

The JSON arrays in [`abi/LaunchToken.json`](abi/LaunchToken.json) and [`abi/SorenVault.json`](abi/SorenVault.json) are generated by `python3 scripts/export_abi.py` from compiled artifacts. `--check` compares them against the pinned build. Solidity NatSpec in the source explains the state-changing entry points.

## Deployment

`LaunchToken()` takes no arguments. `SorenVault(address initialOwner)` takes exactly one address, `$owner` in the manifest. Both constructors are nonpayable. No post-constructor service initialization is required; setting the SORN address is the owner's explicit once-only action from the approved workflow. Neither the token nor application receives any special vault allocation at launch.

`LaunchToken` exposes standard ERC-20 `name`, `symbol`, `decimals`, `totalSupply`, `balanceOf`, `allowance`, `approve`, `transfer`, and `transferFrom`, plus `Transfer`/`Approval` events and standard ERC-6093 errors. There is no administrative token ABI.

## Vault writes

Every function below is nonpayable. Owner operations require `msg.sender == owner()`. All mutations have a reentrancy guard.

| Function | Caller | Effect |
| --- | --- | --- |
| `setToken(address tokenAddress)` | Owner | Lock the token setting; verify code and 18 decimals. |
| `fund(uint256 amount)` | Owner | Pull approved SORN into the vault; irrevocable. |
| `publishChapter(uint256 id, bytes32 answerHash, uint256 prize, string transmission)` | Owner | Open the next funded chapter after its predecessor is solved. |
| `setHint(uint256 id, string text)` | Owner | Set, replace, or clear an open chapter's hint. |
| `commit(uint256 id, bytes32 commitHash)` | Any wallet | Burn 100 SORN and replace that wallet's commitment for the open chapter. |
| `reveal(uint256 id, string answer, bytes32 secret)` | Committing wallet | Validate the preimage, time, and answer; settle the first valid winner. |

`fund` and `commit` require approval on the configured token **to the vault address**, not the burn address. Prefer approving the exact funding amount or `COMMIT_COST()` for one guess. Reveal needs no approval or payment.

## Vault reads

`getChapter(uint256 id)` returns a tuple with these components, in this order:

| Field | ABI type | Meaning |
| --- | --- | --- |
| `status` | `uint8` | 0 = Locked, 1 = Open, 2 = Solved |
| `solver` | `address` | Winning wallet; unset until solved |
| `solvedAt` | `uint256` | Successful reveal's block timestamp |
| `prize` | `uint256` | Promised/paid SORN minor units; retained after settlement |
| `commits` | `uint256` | Successful paid commitments for this chapter |
| `burned` | `uint256` | `commits * 100 * 10**18` |
| `answerHash` | `bytes32` | Published unsalted hash of the correct normalized answer |
| `transmission` | `string` | Original puzzle text, at most 2,000 bytes |
| `hint` | `string` | Latest hint, at most 500 bytes |

`getAllChapters()` returns **`tuple[7]`**, with array index 0 representing chapter 1. Unpublished records are all-zero/empty with Locked status. A solved record retains its original prize and text. Do not sum all `prize` fields to display remaining funds.

| Getter | Return/meaning |
| --- | --- |
| `owner()` | Immutable administrative address |
| `token()` | Configured token address; unset before `TokenSet` |
| `playerStats(address)` | `(uint256 guesses, uint256 burned, uint256 chaptersSolved)` |
| `commitments(uint256 id, address player)` | `(bytes32 commitHash, uint256 blockNumber, uint256 timestamp)`; hash zero means no commitment |
| `lastPublishedChapter()` | Highest published ID, 0–7 |
| `chaptersSolved()` | Number of solved chapters, 0–7 |
| `totalBurned()` | Sum of this vault's successful guess burns; excludes external transfers to the burn address |
| `reservedPrizes()` | The open chapter's reserved prize, or 0 between chapters |
| `totalPrizesPaid()` | Cumulative paid prizes |
| `prizeBalance()` | Configured token's current balance in the vault, including donations and reserves |
| `availablePrizes()` | `prizeBalance() - reservedPrizes()`; unallocated funding, never withdrawable |

Constant getters: `CHAPTER_COUNT = 7`, `COMMIT_COST = 100e18`, `REVEAL_WINDOW = 86400`, `MAX_TRANSMISSION_BYTES = 2000`, `MAX_HINT_BYTES = 500`, and the specified `BURN_ADDRESS`.

`prizeBalance()` and `availablePrizes()` revert before token configuration. The frontend should first read `token()`, render “awaiting token setup” if unset, and display a zero funding total from that known unconfigured state. The chapter/stats getters work before configuration. There is no address enumeration onchain: index `Committed` and `Solved` for the Hall of Decrypters, then read current stats. All players burn the same amount per guess, so guesses and burned leaderboards have equivalent ordering.

## Hashing and the two-transaction flow

Use one normalization function for owner publication and player guessing:

```js
const answer = rawAnswer.toLowerCase().trim().replace(/\s+/gu, "");
```

This convention removes ECMAScript whitespace; it does not perform Unicode NFC/NFKC normalization. Prefer ASCII puzzle answers. All length limits on displayed content are UTF-8 **bytes**, measurable with `new TextEncoder().encode(text).length`. Render transmissions/hints as text rather than trusting their contents as HTML.

With the frontend's ABI library:

```text
answerHash = keccak256(UTF8(answer))
commitHash = keccak256(ABI_ENCODE([string, address, bytes32], [answer, wallet, secret]))
```

`ABI_ENCODE` means Solidity `abi.encode`, not `abi.encodePacked`. There is no chapter, chain, or vault address inside this specified hash; commitments are stored per chapter and per wallet. Use a fresh secret for every commitment, and bind local recovery records to the chain and vault.

1. Generate `secret` from 32 cryptographically random bytes, for example `crypto.getRandomValues(new Uint8Array(32))`. Never use time, a password, `Math.random()`, or a reused public secret.
2. Save `{chainId, vault, wallet, chapter, answer, secret, commitHash}` locally before submission, using storage `try/catch`. Offer a copy/download recovery record and warn if persistence fails. A public transaction hash alone cannot recover the secret. A recovery record is sensitive until settlement.
3. Approve **100 SORN** and submit `commit(id, commitHash)`. Wait for a successful receipt. Use `commitments(id, wallet)` and the committed block's timestamp to establish the window; transaction submission time is not the start time.
4. Enable reveal after a later block is observed. Display a chain-time deadline of `timestamp + 86400`; submit early enough for inclusion by that deadline. Do not enable based solely on local elapsed time. Reconcile receipts after reorgs or a wallet/chain switch.
5. Before revealing, ensure the current stored hash matches the recovery record and the chapter is still open. A later commit replaces the earlier record and incurs another fee. An identical resubmission also charges again and restarts the clocks.
6. Call `reveal(id, answer, secret)` from the same wallet. Only a mined successful reveal wins. A failed or expired reveal, a solved chapter, or a lost secret does not refund a burn. The user may pay for a new commit if the chapter is still open.

The Hero can read `prizeBalance`, `totalBurned`, and `chaptersSolved`. Display a solved prize as paid, not still available. Chapter cards map the three status values to LOCKED, OPEN, and DECRYPTED, with the solver address. Lore can be associated with chapter IDs by the frontend. The contracts do not include the website or offchain narrative assets.

## Events

| Event | Indexed fields | Non-indexed fields |
| --- | --- | --- |
| `TokenSet` | `address token` | — |
| `Funded` | `address funder` | `uint256 amount` |
| `ChapterPublished` | `uint256 id` | `bytes32 answerHash, uint256 prize, string transmission` |
| `HintPosted` | `uint256 id` | `string text` |
| `Committed` | `uint256 id, address player` | `bytes32 commitHash, uint256 blockNumber, uint256 timestamp, uint256 burned` |
| `Solved` | `uint256 id, address solver` | `uint256 prize` |

Failed transactions emit no retained events. `Committed.burned` is the cost of that single commit, not a running total. Direct SORN donations emit the token's `Transfer` event but not the vault's `Funded` event; rely on `prizeBalance` for current funds.

## Custom errors and handling

| Errors | Meaning/action |
| --- | --- |
| `Unauthorized`, `InvalidOwner` | Wrong admin caller or invalid constructor owner. |
| `TokenNotConfigured`, `TokenAlreadySet`, `InvalidToken` | Wait for owner setup; a successful setting cannot be replaced. |
| `InvalidChapter`, `ChapterOutOfOrder`, `PreviousChapterUnsolved`, `ChapterNotOpen` | Invalid ID or state; refresh chapter data. |
| `InvalidAmount`, `InvalidHash`, `TransmissionTooLong`, `HintTooLong` | Validate positive amounts, nonzero hashes, and byte limits. |
| `InsufficientFunding` | Owner must deposit the prize before publication. |
| `NoCommitment` | This wallet has no commitment for this chapter. |
| `RevealTooEarly` | Wait for a block after the stored commit block. |
| `RevealExpired` | Deadline passed; a new paid commit is possible if still open. |
| `CommitmentMismatch` | Wrong answer bytes, secret, wallet, ABI encoding, or replaced commitment. |
| `IncorrectAnswer` | Preimage is valid but the committed guess is wrong. |
| `UnexpectedTokenAmount` | Token balances did not move by the exact required amount; transaction rolled back. |
| `SafeERC20FailedOperation`, token errors | Failed burn/funding/payout; check balance, allowance, and token configuration. |
| `ReentrancyGuardReentrantCall` | A nested mutation was rejected. |

Dependency errors and all exact signatures are present in the generated ABIs. A failed payout preserves the open chapter and winning commitment, so its wallet can retry if the transfer problem is resolved before the same deadline. It receives no deadline extension.
